# Deploying Monoceros to Render

Start to finish, roughly 30 minutes. Render hosts the application, the
PostgreSQL database and the scheduled worker in one project, and gives you a
persistent disk — so you do **not** need Neon, Supabase, or an S3 bucket.

You will need:

- the GitHub repository (already pushed)
- a Render account — <https://render.com>
- a payment card (the smallest paid plans; the free tier sleeps, which delays
  cycle activation and makes the site slow to wake)
- optionally a domain name, and a [Resend](https://resend.com) account for email

---

## 1. Create everything from the blueprint

The repository contains `render.yaml`, which describes the whole stack. Render
reads it and creates all three pieces for you.

1. Sign in to Render.
2. **New → Blueprint**.
3. Connect your GitHub account and pick **`zaddywebbuilds/MONOCEROS`**.
4. Render shows what it will create:
   - `monoceros` — the web service
   - `monoceros-db` — the PostgreSQL database
   - `monoceros-scheduler` — the cron worker
5. It will prompt for the variables the blueprint marks as "not synced". Fill
   them in as below.

| Variable | What to enter |
| --- | --- |
| `APP_URL` | `https://monoceros.onrender.com` — replace with the real service URL Render shows you, or your domain once attached |
| `NEXT_PUBLIC_APP_URL` | Exactly the same value |
| `EMAIL_FROM` | `Monoceros <no-reply@yourdomain.com>` |
| `RESEND_API_KEY` | Leave blank for now |
| `COINGECKO_API_KEY` | Leave blank — the free public tier works |

`AUTH_SECRET` and `CRON_SECRET` are generated by Render automatically. You never
see or set them, and they are not in the repository.

6. **Apply**. The first build takes about five minutes.

> If you are not sure of the URL yet, put a placeholder in `APP_URL` and correct
> it in step 5. `NEXT_PUBLIC_APP_URL` is baked in at build time, so changing it
> later requires a redeploy — Render does that automatically when you save.

---

## 2. Wait for the first deploy

Watch the web service log. Migrations run automatically on every deploy, so you
should see the schema being created before the server starts:

```
Applying migration `20260101000000_init`
✓ Ready
```

When the service is **Live**, open `https://your-service.onrender.com/api/health`.
You should get:

```json
{ "status": "ok", "database": "reachable" }
```

If it says `degraded`, the database is not reachable — check that
`monoceros-db` finished provisioning, then redeploy.

The public site will already load, but the packages section will be empty
because nothing has been seeded yet. That is expected.

---

## 3. Seed the database and create your administrators

Both steps run from **your own computer**, pointed at the Render database. This
works on every Render plan.

1. In Render, open **monoceros-db → Connect → External Connection String** and
   copy it.
2. On your machine, in the project folder, create a temporary file called
   `.env.production.local`:

```
DATABASE_URL=<paste the external connection string here>
```

3. Run the seed and the administrator script against it:

```bash
# Windows PowerShell
$env:DATABASE_URL="<paste external connection string>"
npx prisma migrate deploy
npm run db:seed
npm run admin:create
```

```bash
# macOS / Linux
export DATABASE_URL="<paste external connection string>"
npx prisma migrate deploy
npm run db:seed
npm run admin:create
```

`npm run admin:create` asks for each administrator's email, display name and
password. Input is hidden and only the hash is stored. Create **both**
administrators now.

4. **Delete `.env.production.local`** and close the terminal. The external
   connection string is a production credential — do not leave it lying around
   and never commit it.

> **Never run `npm run db:seed:demo` against production.** It refuses to run when
> `NODE_ENV=production`, but do not tempt it.

---

## 4. Set the payment details

This is the one step nothing works without, and it is deliberate: the platform
ships with the wallet blank so no one can ever pay into a placeholder address.

1. Go to `https://your-service.onrender.com/admin/login`.
2. Sign in with the first administrator account.
3. The overview shows a warning: *"Payments are not configured."*
4. **Settings → Payments**, and set:
   - **Payment network** — the chain you actually accept, e.g. `TRC20`
   - **Company USDT wallet address** — the receiving address
5. Save.

**Have the second administrator independently check the address before you
accept a single payment.** The platform notifies every staff account and writes
a dedicated audit entry whenever it changes, precisely so this gets noticed.

While you are in Settings, also fill in **General** (company name, address),
**Support** (email, WhatsApp number) and **Legal** — leaving the registration
number blank unless the company genuinely holds one. The site omits what is
unset rather than inventing it.

---

## 5. Attach your domain

1. **monoceros → Settings → Custom Domains → Add**.
2. Add the CNAME record Render gives you at your domain registrar.
3. Wait for the certificate (usually a few minutes; Render handles TLS).
4. Update `APP_URL` **and** `NEXT_PUBLIC_APP_URL` to the new address and save —
   Render redeploys automatically.

Email links, canonical URLs and the sitemap all follow `APP_URL`, so this step
matters before you invite real users.

---

## 6. Turn on real email

Until you do this, `EMAIL_PROVIDER=console` writes every message to the Render
log instead of sending it. Verification links and payment notifications will not
reach anyone.

1. Create a [Resend](https://resend.com) account and verify your sending domain.
2. Create an API key.
3. In Render, on **both** `monoceros` and `monoceros-scheduler`, set:
   - `EMAIL_PROVIDER` = `resend`
   - `RESEND_API_KEY` = your key
   - `EMAIL_FROM` = `Monoceros <no-reply@yourdomain.com>`
4. Save. Both services redeploy.

Test it by registering a throwaway account and confirming the email arrives.

Any SMTP relay works too — set `EMAIL_PROVIDER=smtp` with `SMTP_HOST`,
`SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` and `SMTP_SECURE`.

---

## 7. Check the scheduler

`monoceros-scheduler` runs every five minutes. Open it in Render and look at a
recent run:

```
Scheduled run complete
  cycles activated ....... 0
  investments activated .. 0
  investments matured .... 0
```

Zeros are correct when nothing is due. What matters is that it **runs and
exits cleanly**. If it never runs, cycles will not open on Friday and terms will
not mature on time.

---

## Go-live checklist

- [ ] `/api/health` returns `ok`
- [ ] Packages appear on `/packages`
- [ ] Both administrators can sign in at `/admin/login`
- [ ] Payment network and wallet address set, **verified by a second person**
- [ ] Company details, support email and WhatsApp number filled in
- [ ] Legal pages reviewed — no licence or registration number published unless genuinely held
- [ ] Custom domain attached, `APP_URL` and `NEXT_PUBLIC_APP_URL` updated
- [ ] Real email provider configured and a test message received
- [ ] Scheduler showing successful runs
- [ ] Demo data absent (`db:seed:demo` never run against production)
- [ ] External database connection string deleted from your machine

when idle, which delays cycle activation and makes the first page load slow —
not appropriate for a platform holding customer money.

Scale the database and disk up as the number of investors and stored identity
documents grows.

## Ongoing operations

**Deploying a change.** Push to `main`. Render rebuilds, runs
`prisma migrate deploy`, and swaps traffic over only once `/api/health` passes.

**Backups.** Render Postgres takes daily backups on paid plans. Check the
retention on your plan and take your own dump before anything risky:

```bash
pg_dump "<external connection string>" > monoceros-backup.sql
```

**Watching for trouble.** The audit log at `/admin/audit` records every
sensitive action. Review wallet address changes and payment approvals routinely.

**If the scheduler is down.** Nothing is corrupted — everything is derived from
stored timestamps, so activation simply happens late. Once the worker runs
again it catches up in one pass. You can also trigger it by hand from
**Admin → Investment cycles** for a boundary that has already passed; that
action requires a reason and is audited.
